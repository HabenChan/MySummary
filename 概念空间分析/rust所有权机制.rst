Rust所有权机制
**************

本文对Rust的所有权机制做一个概念建模。

Rust的所有权机制主要目的是避免UAF（Use After Free），避免使用非法指针。它的基
础还是“如果内存对象有引用，内存就不能释放”。为了做到这一点，Rust（的安全代码）
不支持指针，只支持引用。指针可以作为一个数值存在，但引用永远是有类型的，你只能
用来访问被引用的对象，并不能直接当作一个数值使用。

在释放方面，和Java/Python这种在没有引用后自动释放内存的策略不同，Rust的策略是
反过来的：要求引用不能超出内存对象的存活期使用。

几乎所有的高级编程语言都提供两种内存变量（类型）：

* 栈变量：仅在作用域之内有效，离开作用域自动释放。比如函数内定义的变量，离开函
  数就失效。

* 堆变量：全局有效，在主动释放前可以一直存在。比如用malloc()函数分配的内存。这
  个概念其实可以推广，所有全局资源都可以认为是一种堆变量，比如io通道，也是需要
  分配后使用，用完需要归还的，如果提前归还是有可能造成UAF的。

Rust没有指针，所以你不能直接使用malloc()，它的所有堆分配都是封装成对象的（对象
内部是unsafe的代码，你的safe代码只能使用这种对象）。这种对象的meta data可能在
栈上，但主体数据则在堆上分配。meta data和堆上的主体数据全部属于这个对象，这个
对象无效了，它的栈和堆都一起无效。

这样造就了Rust两种变量：

* Copy变量：支持Copy属性（Rust通过Trait定义变量的属性，后面我们统一称为Trait）
  的变量，这种变量不允许带堆，发生赋值的时候直接拷贝内容。
* Move变量：不支持Copy Trait的变量，这种变量如果发生赋值，只拷贝meta data，堆
  上的空间是复用原来的。如果发生这种赋值，旧变量自动无效，不能再使用。

.. note::

  注意：copy过程是统一的内容拷贝，不调用任何拷贝函数，Copy Trait也不包含copy()
  函数，所以，你不能通过写一个拷贝函数让带堆变量变成Copy变量。要拷贝一个带堆变
  量，你只能实现Clone Trait，用主动的clone()函数实现拷贝，这不能依靠赋值去完成。

看个例子：::

  {
    let a: i32 = 10;                        // 创建一个copy变量
    let b: i32 = a;
    // 这里还能使用a
  
    let c: String = String::from("hello");  // 创建一个move变量
    let d: String = c;                      // c对堆的所有权转移到d
    // 这里不能再使用c了
  }

所有这些变量，只要离开当前上下文，无论堆还是栈，全部自动释放，除非使用全局变量
（不推荐），否则你的堆资源一定被一个栈资源所拥有，这个栈离开了作用域，它的堆资
源也会跟着一起释放。在上面的例子中，离开最后一个大括号后，d的"hello"资源会被自
动释放。

这是所有权机制最基本的原理：把堆资源和一个名字绑定，这个名字无效的时候，堆资源
一起无效。

我这里特意把这种带堆的变量称为Move变量，而不叫它对堆的“索引”，因为Rust是专门有
索引的。考虑一下这个代码片段：::

  let a = String::from("hello");    // 创建move变量
  test(a);                          // move到test的第一个形参中
  // 失去a的控制权

一旦我们进行函数调用，我们move到另一个变量中，我们就失去对这个变量的控制权了，
这样代码就很难写了，除非你任何时候都传所有的数据：::

  let a = String::from("hello");    // 创建move变量
  let b = a.clone();                // 拷贝一份全部数据（堆中会多一个"hello"）
  test(b);
  // 失去b的控制权，但a的控制权还在

但要求用户任何时候都用值传递数据，这个限制就太大了。所以，它还是可以支持引用的，
上面的代码就可以写成这样：::

  let a = String::from("hello"); // 创建move变量
  let b = &a;  // 这只是为了容易看，你完全可以省略这句直接写test(&a)
  test(b);
  // a仍然有效

为了说清楚这个问题，让我们引入一个新概念：Name Binding。我中文上把它叫“名字”。
我们说一个“变量”的时候，说的是它占着的那些内存，变量的名字是绑定那些内存的。而
当我们定义一个对这个变量的“引用”的时候，这个引用也有一个名字，这个名字是绑定那
个引用的。这两者是不同的。在上面的例子中，a是变量的绑定，b是引用的绑定。最终都
是为了说那片内存，但两者在讨论到细节的时候，很容易造成误会。特别是，在读访问的
时候，Rust常常可以自动解引用：比如这里的*b就是对b解引用，它表示a。但很多场景都
支持自动解引用，你可以直接通过b来访问a的内容，看起来b也可以直接当作a来用。但这
只是语法糖，不表示两者是一样的。

这里还有一个微妙的问题：Rust带堆的变量，它的meta data其实就是对堆内容的一个“引
用”，但这是我们自然语言感知到的“引用”，不是Rust语言中的引用。但如果我们向下看
到这些带堆变量的实现，我们还是会谈到“引用”，比如String的内部实现是这样的：::

  struct String { vec: Vec<u8>, }
  struct Vec<T> {
    ptr: *mut T,
    len: usize,
    cap: usize,
  }

这里这个ptr就是对T的裸指针“引用”（这种裸引用本身可以是safe的，对裸指针解引用才
unsafe）。所以，你说String本身也是一种对某个堆内存的“引用”，自然语言上也是说得
通的。

所以，Rust中，你只会有三种函数返回值：

* Rust意义上的引用。这个引用要不来自某个输入，要不来自其他全局资源。
* Move变量。通过move把堆数据转送给调用者，比如你返回一个String。返回值整个move
  到调用者的变量上，堆也被move到了上一层，生命周期按上一层的那个Binding来算。
* Copy变量。通过值拷贝直接送入。

这样，我们又有潜在的UAF的问题了。我们前面说过，Rust的策略不是自动根据引用的生
命周期决定变量的生命周期，而是如果你写了引用有可能超出被引用者生命周期的代码，
它直接不让你编译通过。所以它的规则是：

* 变量本体失效，引用必须失效
* 如果有可写引用（主动写&mut定义的引用），其他所有引用必须失效

这样就没有UAF了。看个例子：::

  let a = String::from("hello");
  let b:& String;        // 定义一个未初始化的引用（这是允许的）
  b = {
    let c = String::from("hello");
    match cond {
      OPT1 => &c,   // 这里就会报错，认为b活得比c长，不能用来引用c
      _ => &a,
    }
  };

这里例子说明：Rust并不考虑你运行期走什么路径，它判断的是“可能性”，只要存在UAF
这个可能性，它的判断器（称为borrow checker）就认为这个逻辑是错的。

而且，老实说，我一开始是看不出报错会出现在b=&c这个位置上的，我认为应该出现在使
用b的时候。但这不重要，这说明这不是一种C语言那样每个动作都有可明确预期的语言，
你只能有一个大致的理解方向，然后具体问题具体分析。

这么说起来，其实Rust讨人嫌不是没有道理的，它其实限制了你原来写程序的自由度，就
算你逻辑上根本不会有问题（比如这里你可能根据条件在b等于&a的情况下在后面使用b），
但编译就不让你这么写。

这还不是最麻烦的，更麻烦的是跨模块以后如何还能保持这些范围判断的问题。还是用上
面的例子来说：::

  let a = String::from("hello"); // 创建move变量
  let b = test(&a);

我们把a的引用给了test，你怎么知道test有没有把a的引用给到b这个对象内部呢？如果b
里面有a的引用，那么后面我们调用b的方法的时候，会不会因为b比a活得长而导致UAF呢？

Rust又是编译型语言，每个模块是独立编译的，我们编译这段代码的时候没法知道test的
实现是什么样的。所以，它有什么性质，我们就必须从签名上可以看出来。

为此，我们需要这样定义test的签名：::

  fn test(a: &'a String) -> &'a B;

除了多个一个'a，其他部分都没有什么特别的。这个'a就定义了一个生命周期。这个定义
完整形态是这样的：::

  fn test<'a>(a: &'a String) -> &'a B;

这个test现在是一个泛型，带着一个泛型参数'a，当这个参数应用到函数上，它表示：
“存在一个作用域'a，使输入的a参数和输出的&B都有效”。我们调用这个函数的时候，输
入已经有一个作用域范围了，'a肯定是这个范围的子集，返回值的范围也必须是这个范围
的子集。经过这个规则检查，你就无法写出返回值的生命周期可能超过输入的生命周期的
程序。

上面这个函数，我们用了B的引用返回，由于我们没有输入B，这个B就只能从全局变量
（生命周期'static）上获取，否则函数内部自己创建一个新的对象是传递不出来的。更
常见的方法是返回B，而不是B的引用。这样我们就要把这个生命周期参数传递到B内部，
这个B就必须是个泛型：::

  struct B<'a> { str_ref: &'a String, }
    
这表示B需要根据具体的生命周期的不同，定义它的成员的生命周期。上面这个定义说明：
当B<'a>被实例化的时候，所实例化的对象和str_ref必须有一个共有的生命周期'a。

自然语言的理解就是：str_ref指向的对象不能比B的生命周期短，从而保证只要B还能用，
B里面的str_ref都还能用。

这些定义，从好的一面来说，避免了你UAF，从坏的一面来说，白白让你写程序在代码逻
辑之外增加很多额外的限制，让你更难思考。极端一点比喻就是要用不规则的砖盖房子，
你不肯定什么地方可能会超出你的预想。后面我们会看到更多为了绕过这些障碍而增加的
基础设施。

我们再看看这个“只允许一个mut引用”的规则。首先，这个mut控制的是名字（Binding）
能不能修改的问题，不决定你能不能修改内存。看个例子：::

  let a = 10;
  let a = 11;       // 这是允许的，a“遮盖”了前一个a的定义，这是一个新的名字
  a = 12;           // 这是不允许的，因为a现在绑定在11这个值上，而a默认是immutable的

  let mut b = 11;
  b = 12;           // 这是允许的，b绑定的对象可以修改

  let c = Cell::new(10); // 只读定义
  let d = &c;       // 只读引用
  d.set(11);        // 修改里面的内容，这是允许的。

你可以看到，在程序的最后，我们虽然只有Cell(10)（我们这样表达内容是10的Cell）的
只读引用，但我们还是可以修改里面的值。Rust的mut关键字保护的是那个Binding，而不
是里面的内容。

所以，只允许一个mut引用，保护的是对象修改的完整性。像这里这个Cell，你只能用
get/ set整体读写里面的内容，不能单独修改其中一个域。如果你自己定义了一个变量，
你定义一个函数去修改它，你要求引用是mut的，那么编译器已经帮你检查了：现在只有
你拿着这个对象，没有任何其他人拿到它了（包括原始定义的binding也会被临时锁住）。

这样，我们就又多了一个Cell这样的封装对象，你明明可以使用一个变量10的，为了多个
模块可以修改它，你还不能写let a=10，你要写let a=Cell::new(10);

类似的还有RefCell，它没有set/get()函数，它是个动态的借用规则执行器。你可以先
borrow()借一个读引用，或者用borrow_mut()获得唯一的可写引用，再进行修改。如果规
则冲突，对应的函数还是可以panic的。

Cell/RefCell:new()定义的是个对象，它的结果是move到被定义的binding中的，所以如
果你在函数上下文直接let a = Cell::new(10)，这个a整个都在堆栈中。但如果你里面的
内容很大（比如是个数组），你可以放到堆上，这个东西就会写成这样：::

  let a = Box::new(Cell::new(10));

这不是互相取代的关系，Box帮你在栈上留一个meta，实际数据在堆上，而Cell是保证你
可以整体set/get而已。

如果你要让多个线程或者协程共享，那么我们不知道谁先释放，我们就需要这样写：::

  let a = Rc::new(Box::new(Cell::new(10)));    // 一般引用计数，用于协程一类上下文
  let a = Arc::new(Box::new(Cell::new(10)));   // 原子引用计数，用于线程一类上下文

  thread_a = a.clone();
  xxx::spawn(move || { thread_a... });         // 这是伪码示意

（注：这个例子为了说明情况，其实过度复杂化了：Box的功能其实可以被Rc/Arc取代，
但考虑如果我们需要的不是单个值，而是一个数组，那么这里我们还需要Vec，问题是一
样的。）

所以，你看着Rust好像只是引入了一点点的约束，但“开其兑，济其事，终身不救”，那一
点点约束，展开以后就会引入一大堆的逻辑。Rust难推广，这是很重要的原因。
